# Architecture: Meridian.Interchange

This page has two drawings of the same worker, both written by `sliderule render`. Read this
before the fence, because this is the thin one and the thinness is the lesson.

Twelve rules hold Meridian.Interchange and eleven of them draw nothing. That is not a gap in the
drawing. Canonical .NET guidance is almost entirely non-spatial. It tells you to reuse an
`HttpClient`, to accept a `CancellationToken` and to suffix a `Task`-returning method with `Async`.
It also tells you not to resolve services from the provider or capture a scoped dependency in a
singleton. Every one of those is about how a type is built, called or named. None is a relation
between two regions of code, so none has an arrow.

The list under the fence is where the law of this subsystem lives, and
`sliderule explain <rule-id>` is how it is read.

The one rule with a direction is `contracts/no-entity-exposure`, and it is the only rule drawn
inside the fence. `OutboxMessage` is a persisted entity, and the rule says no public signature
outside the `Outbox` namespace may hand one out. That is a relation between two places, so it draws.
The drawing shows an `expose` arrow from the subsystem to the type it must keep to itself. The
rounded box is how the drawing marks a place named only as the target of a rule, which is what
`OutboxMessage` is here. The law points at it; the law does not govern what happens inside it.

The other eleven are named by ID and expanded on demand. Nine of them come from a shared rule pack,
so `explain` prints the pack's reason together with the learn.microsoft.com page behind it. A spec
whose rules are mostly citations produces a page that is mostly citations, and no drawing can carry
a citation.

That is the shape the law gives the pair on this codebase. The tool says so rather than drawing
something that would look fuller than the law is.
