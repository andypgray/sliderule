# SlideRule: architecture for agents

## The self-hosting principle

A compiler that cannot compile itself is not trusted with anyone else's source. SlideRule accepts the same test, and this repository is the tool's own first consumer. The spec in `arch/SlideRule.Architecture` governs this code. Every read command runs against this solution in CI: `check`, `render`, `status`, `graph` and `explain`. The xUnit adapter runs the same rules as individually named tests. The renderer writes 15 committed artifacts here, and a test recomposes each one and fails on drift. They are the block below, the diagram in `ARCHITECTURE.md`, 12 per-directory cards and the model file `sliderule.model.json`. One of those tests also fails on a committed card that no rule placement produced. A card orphaned by a spec change therefore cannot stay here to be read. CI runs `render --check` over the repository, which fails on any file a render would change. A card the spec now places where none is committed is one of them. Of the commands, only `baseline` has no gate pointing at this repository. It is the human escape valve, and a gate that ran it would be moving the ratchet. The build analyzer runs over this repository's own projects as its last released package. CI fails the build on any diagnostic it reports here, as it does on the four example solutions.

The feedback loop is live in this working copy. A `Stop` hook, with a `SubagentStop` twin for workers, runs `check` when a turn ends and blocks the stop on a red rule. The agent then reads the report and keeps working instead of handing back code that breaks a law. A registered MCP server answers architecture queries in the same session. Claude Code sessions here read this file and the cards next to it too. They do so through a local `@AGENTS.md` import and Claude Code's option to read both `CLAUDE.md` and `AGENTS.md`. That wiring is machine-local, so a clone gets the `hooks/` directory instead. It has the config snippet, whose entries run `sliderule hook`, and the launcher that keeps a warm server from holding this repository's build outputs. The directory's README, [`hooks/README.md`](hooks/README.md), explains what to paste where. The contract `sliderule hook` implements does not rest on anyone's local setup. Tests drive it across the whole exit-code mapping, over real git repositories and a real linked worktree. CI installs the packed global tool and walks the README quickstart end to end. It also scaffolds the spec project the `derive_spec` recipe publishes, `PackageReference` included, out of that same pack. It does so once on a repository that pins package versions per project and again on one that manages them centrally. Each run must be green on conforming code and red on a violation. It must be red again when the one line that keeps a single csproj valid on both is deleted. The repository is the evidence for the product's claim that rules cannot drift and prose cannot rot.

Three rules follow for any agent working here:

1. **Consumption is part of done.** A surface, command, or recommendation is finished only when this repository itself uses it. When you add a capability, wire this repository's own use of it into the same change. If you cannot, say so in your report.
2. **No claim before it is live.** Documentation here states what this repository already practices, and never what it intends to.
3. **A self-consumption gap outranks new work.** Any place this repository fails its own standards contradicts the claim above; treat it as an embarrassment, not a backlog item. Raise it as a defect, and do not work around it silently.

## Architecture (SlideRule)

reference = a source-level type reference; use = a source-level member access; construct = a source-level object creation (`new`, including target-typed `new()`); inject = a source-level constructor-parameter dependency (primary constructors included); catch = a source-level `catch` clause (a bare `catch` counts as `System.Exception`); throw = a source-level `throw` of the thrown expression's type (bare rethrows `throw;` are not recorded). Expand any rule ID with `sliderule explain <rule-id>`.

registered = named in a source-level container registration (`AddSingleton`/`AddScoped`/`AddTransient`/`TryAdd*`/`AddHostedService`/`AddDbContext`/`AddHttpClient<TClient>`); registrations made by assembly scanning, factory internals, or framework defaults are not seen.

### Layers
- **Core** — project `SlideRule`. Core is the package a spec is written against: the fluent language, the model a spec compiles to, and the readers of that model that need no compiler.
- **Model** — types in the Core layer in `SlideRule.Model.*`. Model is the reified spec: the nodes a spec compiles to, and the one thing the checker and the renderers both read.
- **Checking** — types in the Core layer in `SlideRule.Checking.*`. Checking evaluates each rule of the model against an extracted codebase: a verdict per rule, its violations, and what the baselines grandfather.
- **Rendering** — types in the Core layer in `SlideRule.Rendering.*`. Rendering turns the model and a check's results into what people and agents read: the managed block and cards, the diagrams, and the reports.
- **Extraction** — project `SlideRule.Extraction`. Extraction reads a compilation into a fragment of the codebase model and merges the fragments into the model the checker evaluates against, using the compiler API and nothing else.
- **Analyzers** — project `SlideRule.Analyzers`. Analyzers runs the extractor and the checker inside the C# compiler, over the one project being built, and reports a broken rule as a warning at the offending code, in the editor as it is typed and in the build.
- **SpecAnalyzers** — project `SlideRule.SpecAnalyzers`. SpecAnalyzers runs Core's literal checks inside the C# compiler, over a spec project as it is written, and reports a bad string literal as a warning on the literal.
- **SpecCompletion** — project `SlideRule.SpecCompletion`. SpecCompletion offers the namespaces and types a spec can anchor on inside the editor a spec is written in, reading the same slot markers the spec analyzer reads.
- **Workspace** — project `SlideRule.Roslyn`. Workspace is the Roslyn host: it loads a solution through MSBuild or a build log, hands each compilation to Extraction, and keeps the extraction cache and the baseline files.
- **Host** — project `SlideRule.Cli`. Host is the `sliderule` command: the CLI verbs, the MCP server, and the spec loading and pipeline behind both.
- **Adapter** — project `SlideRule.Xunit`. Adapter runs every rule of a spec as an individually named xUnit test in the consumer's own test project.
- **Pack** — project `SlideRule.Packs.DotNet`. Pack is the shared rule pack: canonical .NET rules as an ordinary class library that a spec takes one method at a time.

### Rules
- `layering/core-no-roslyn` — The Core layer must not reference the Extraction layer, the Workspace layer, types in `Microsoft.CodeAnalysis.*` or types in `Microsoft.Build.*`. Core is the netstandard2.0 reified model both render targets consume; reading a compilation is the work of the two layers above it, and a Microsoft.CodeAnalysis or Microsoft.Build package reference would leak compiler types into Core just as a project reference to either layer would.
- `layering/extraction-compiler-only` — The Extraction layer must not reference the Workspace layer, the Host layer, the Adapter layer, the Pack layer, types in `Microsoft.Build.*` or types in `Microsoft.CodeAnalysis.MSBuild.*`. The extractor runs wherever a compilation exists, with no workspace and no build engine behind it, and that holds only while the compiler API is the whole of what it needs. The build already refuses a project reference up to Workspace, Host or Adapter, since each of them depends on this project. What it does not refuse is a package: a reference to Microsoft.Build or to the MSBuild workspace compiles, passes every test, and leaves an assembly that loads only in a process that can also load MSBuild.
- `layering/analyzers-compiler-only` — The Analyzers layer must not reference the Workspace layer, types in `Microsoft.Build.*` or types in `Microsoft.CodeAnalysis.MSBuild.*`. The analyzer is loaded by whichever compiler is building the project: csc on the command line, the compiler server, Visual Studio. None of them has a workspace or a build engine to give it, and an assembly that needs either does not load there. The compiler reports that as one warning about the analyzer and carries on without it, so the build goes quiet where it should have gone red.
- `layering/model-independent` — The Model layer must not reference the Checking layer or the Rendering layer. The Model is the one reified thing this product is built around: a spec compiles to it, and checking and rendering are two independent readers of it. A reference the other way would make the model know about a consumer, and the next render target could no longer be added without touching it.
- `layering/no-circular-references` — Each of the Model, Checking and Rendering layers must not have circular references with the others. Model, Checking and Rendering are three cuts inside one assembly with one intended direction: a model and two readers of it. A circle among them means a reader has become something the other reader depends on, and the next render target or checker change could no longer land without touching both.
- `layering/leaves-independent` — Each of the Host, Adapter, Pack, Analyzers, SpecAnalyzers and SpecCompletion layers must not reference the others. Host, Adapter, Pack, Analyzers, SpecAnalyzers and SpecCompletion are the six leaves of the project graph: each is a different way to consume Core, and none is a dependency of another. A reference between two leaves would pull one consumer's closure — the CLI's MSBuild and MCP machinery, the adapter's xunit, the pack's canonical rules, an analyzer's compiler host — into a project that ships without it.
- `layering/pack-depends-on-core-only` — The Pack layer must reference only the Core layer (external packages are not constrained by this rule). A spec project takes the rule pack as a reference of its own, and the whole of what the pack needs is the Arch it composes onto. A reference to the Workspace layer or the CLI would pull MSBuild and the rest of the tool into the closure of every spec project that takes the pack — and nothing in the project graph stops it, because the pack is a leaf and no reference out of it would be circular.
- `layering/spec-analyzers-depend-on-core-only` — The SpecAnalyzers layer must reference only the Core layer (external packages are not constrained by this rule). The spec analyzer ships inside the contract package, in a directory that holds it and one neighbour, Core, and a compiler resolves an analyzer's dependencies from that directory and nowhere else. A reference to Extraction or to any other project here compiles and passes every test, because the test process can load it, and then fails to load inside the compiler of everyone who references the package. The sibling analyzer project references Extraction and is the obvious thing to copy, and nothing in the project graph stops it, because this project is a leaf.
- `layering/spec-completion-stands-alone` — The SpecCompletion layer must reference only itself (external packages are not constrained by this rule). An editor builds a project's completion providers by reflection, inside handlers that report nothing, so an assembly it cannot load produces no list and no message anywhere. This one ships in the contract package's analyzer directory beside the contract and the spec analyzer, and a reference to either compiles, passes every test and then fails to load in the editor of everyone who references the package, where the only symptom is a list that never appears. Nothing in the project graph stops it, because this project is a leaf.
- `layering/adapter-is-a-leaf` — The Adapter layer must not be referenced by the Core layer, the Extraction layer or the Workspace layer. The adapter rides xunit.v3; a product reference would ship a test framework to every consumer of the referencing package. Host, Pack, Analyzers, SpecAnalyzers and SpecCompletion are the other five leaves, and layering/leaves-independent already holds all six off each other, so this rule names only what sits below the adapter.
- `api/core-front-door` — Types in `SlideRule` must belong to `Accessibility`, `Arch`, `Constraint`, `FieldSelectionConstraints`, `IArchitectureSpec`, `IAttributeInfo`, `IMemberInfo`, `IPackageReferenceInfo`, `IParameterInfo`, `IProjectInfo`, `IRuleBuilder`, `IScopeBuilder`, `ITypeInfo`, `Layer`, `Lifetime`, `Member`, `MemberKind`, `MemberSelectionAdjectives`, `MemberSelectionConstraints`, `MethodSelectionConstraints`, `MigrationPolicy`, `ProjectSelectionAdjectives`, `ProjectSelectionConstraints`, `PropertySelectionConstraints`, `Selection`, `SelectionAdjectives`, `SelectionConstraints`, `SpecValidation` or `TypeKind`. The root namespace is the authoring surface. Someone writes `using SlideRule;` and what completion offers from there is, in practice, the whole language they believe exists — so a type that lands in it uninvited is one more thing to read past before finding the verb they wanted, and that cost falls in the first hour with the product. Hiding the rest is free: member resolution on a return type ignores using directives, so a chain keeps flowing through types nobody imports.
- `api/extraction-front-door` — Types in `SlideRule.Extraction`, except private types, must belong to types named `CodebaseModelBuilder`, `CompilationInput`, `ExtractionInputs`, `FragmentExtractor`, `FragmentMerger`, `ProjectArtifactFacts` or `SiblingProjects`. The root of this assembly is what a host calls to turn compilations into a codebase model: the input it fills in, the extractor, the merger, and the builder that runs both. The fragment records and the passes sit in namespaces behind it so that they stay free to change shape. A type left in the root reads as one more thing a host may call, and the first host to take it up turns the next rearrangement of the extractor's internals into a break in every process that loads it.
- `api/workspace-front-door` — Types in `SlideRule.Roslyn` must belong to types named `CodebaseExtractor`, `LoadedSolution`, `PathCanonicalizer`, `SolutionDiscovery`, `UserErrorException`, `WorkspaceLoader`, `WorkspaceSession` or `WorkspaceSnapshot`. This assembly travels inside the tool and the xUnit adapter, and its root is the seam those two hosts call, which leaves everything behind it free to be rearranged. A type left sitting in the root reads as part of that seam, and the first host to take it up ties the next rearrangement of the internals to a change in both hosts.
- `api/host-front-door` — Types in `SlideRule.Cli` must belong to types named `CliEntry`, `CliErrorMapper`, `CommandEntryPoint` or `CommandFactory`. Namespaces are not API here — this project ships as a tool — so the only thing the root namespace buys is legibility, and that is worth holding. The entry path is the first thing anyone reads to learn how the tool starts, and a root that also holds the verb requests, runners and pipeline stages it dispatches to hides that path among the thirty types it calls.
- `model/constraint-nodes` — Types in the Core layer named `*Constraint`, except `Constraint`, must reside in `SlideRule.Model.*`. A `*Constraint` is a node of the reified model — what a spec compiles to and what both render targets read back. The checker's dispatch and the sentence renderer each switch over the whole set, so a constraint node declared somewhere else is one they would silently not handle. `Constraint` itself is the public base a spec author names, so it stays in the root namespace with the rest of the authoring surface.
- `model/reified-nodes-immutable` — Properties of types derived from `Selection`, types derived from `Constraint`, types derived from `MemberSelection` or types derived from `ProjectSelection` must be get-only. A spec compiles to these nodes and both render targets read them back, so a node is a value: the same spec must render the same sentence and check to the same verdict whoever walks it, and a settable property is the one way a walker could change what the next walker sees. The four roots are the whole reified hierarchy an author can name — a selection, a constraint, the member selection a projection mints, and the project selection the artifact noun mints — and their private-protected constructors mean no assembly outside Core can add a fifth. The BUILDERS are deliberately outside this law and stay mutable: a RuleRegistration accumulates a posture and a constraint across chained calls, which is what makes the stage machine a stage machine.
- `packaging/core-netstandard-only` — Project `SlideRule` must target only `netstandard2.0`. netstandard2.0 is the one TFM a net48 spec project and the net10 host can both load; Core is the contract every spec references, so its TFM is the product's reach.
- `packaging/core-carries-nothing` — Project `SlideRule` must reference no NuGet packages other than private ones, whose `PrivateAssets` is `all` (declared references only; transitive dependencies are not seen). Every consumer's spec csproj takes Core directly; a package Core drags along is imposed on every estate that adopts the tool, and a net48 spec has to resolve it too.
- `packaging/shipping-locks-restore` — Packable projects matching `SlideRule*` must lock package restore. CI restores locked; a shipping project without a lock file floats its dependency graph under audit. See <https://learn.microsoft.com/nuget/consume-packages/package-references-in-project-files#locking-dependencies>.
- `packaging/only-the-named-ship` — Projects matching `SlideRule*`, except projects `SlideRule`, `SlideRule.Analyzers`, `SlideRule.Xunit` or `SlideRule.Cli`, must not be packable. Only the packages named in this rule ship, and the SDK packs by default, so a project that stays silent about it is one release-pipeline accident away from publishing this repository's internals under a name nobody reviewed.
- `di/no-captive-dependencies` — Singleton-registered types in `SlideRule.*` must not inject scoped-registered types or transient-registered types. The MCP server is one long-lived process wired all-singleton by design (IEnvironment, WorkspaceSession, SessionFragmentStore, SpecModelCache, SpecResolutionCache, ISolutionSource); a scoped or transient service injected into a singleton is captured for the whole process and silently shared across every tool call. See <https://learn.microsoft.com/dotnet/core/extensions/dependency-injection/guidelines>.
- `di/no-service-locator` — Types in the Host layer, except types named `McpServerCommand` or `GlobalCallToolFilter`, must not use `IServiceProvider.GetService()`, `ServiceProviderServiceExtensions.GetService()` or `ServiceProviderServiceExtensions.GetRequiredService()`. Resolving services from IServiceProvider at call sites hides a type's real dependencies; declare them as constructor parameters. See <https://learn.microsoft.com/dotnet/core/extensions/dependency-injection/guidelines>.
- `di/no-buildserviceprovider` — Types in `SlideRule.*` must not use `ServiceCollectionContainerBuilderExtensions.BuildServiceProvider()`. Calling BuildServiceProvider while configuring services builds a second container with its own singletons, a duplicate-instance trap. See <https://learn.microsoft.com/dotnet/core/extensions/dependency-injection/guidelines>.
- `cli/no-stdout` — The Host layer must not use `Console.Out`, `Console.Write()` or `Console.WriteLine()`. Stdout is a protocol channel here — the MCP server speaks JSON-RPC over it and CLI output flows through System.CommandLine's console — so a direct Console write corrupts the wire and is invisible to the in-process tests. See <https://modelcontextprotocol.io/specification/2025-06-18/basic/transports#stdio>.
- `mcp/tools-accept-cancellation` — `[McpServerTool]`-attributed methods of types in `SlideRule.*` must accept a parameter of type `CancellationToken`. Tool calls run inside one long-lived server process; a tool method without a CancellationToken cannot honor a client cancel and holds the idle watchdog open. See <https://modelcontextprotocol.io/specification/2025-06-18/basic/utilities/cancellation>.
- `mcp/tool-types-attributed` — Types in `SlideRule.Cli.Mcp.Tools.*` must be attributed with `[McpServerToolType]`. Tool discovery is the attribute walk: WithCoercingTools registers the [McpServerTool] methods of [McpServerToolType]-annotated classes, so a tool class without the type attribute compiles, registers nothing, and its tools silently vanish from the server.
- `mcp/tool-types-in-cli` — Types attributed with `[McpServerToolType]` must reside in project `SlideRule.Cli`. The converse of mcp/tool-types-attributed: that rule keeps every type in the tools namespace attributed, and this one keeps every attributed type in the CLI. The ModelContextProtocol SDK is the CLI's package reference alone, so a tool class declared in Core or Roslyn would drag the SDK into that package's closure — Core's rides into every spec project that references the contract library.
- `mcp/no-blocking-waits` — Types in the Host, Workspace or Extraction layers, except types named `ServerShutdown`, must not use `Task.Wait()`, `Task<TResult>.Result`, `ValueTask<TResult>.Result`, `TaskAwaiter.GetResult()`, `TaskAwaiter<TResult>.GetResult()`, `ValueTaskAwaiter.GetResult()` or `ValueTaskAwaiter<TResult>.GetResult()`. The CLI and the two layers under it are one long-lived MCP server as often as they are a one-shot command, and a blocking wait there costs twice: it holds a thread-pool thread for as long as the child process or workspace load it waits on, and it drops the CancellationToken the tool call was handed, so a client cancel leaves a zombie running the timeout out instead. ServerShutdown is the one sanctioned block — a bounded drain at process exit, with nothing left to starve. See <https://learn.microsoft.com/dotnet/csharp/asynchronous-programming/async-scenarios>.
- `mcp/no-path-assembly-loads` — Types in the Host layer, except types named `SpecLoadContext`, must not use `AssemblyLoadContext.LoadFromAssemblyPath()`. A host that loads an assembly from its path pins that file for as long as the host lives, and this host lives for a whole session: the model roots the spec's Types, so the collectible context never collects and the operating system never releases the build output. Every rebuild of what was loaded then fails, and the only cure is killing the server — which for a stdio server is terminal, because the client never reconnects one, so the session's architecture queries go dead with no error anywhere. SpecLoadContext is the single sanctioned caller: it reads bytes, and reaches for the loader only when the file is already gone.
- `mcp/warm-state-constructed-once` — Types in the Host layer, except types named `McpServerCommand`, must not construct types named `WorkspaceSession`, `SessionFragmentStore`, `SpecModelCache` or `SpecResolutionCache`. The warm server holds exactly one of each piece of session state for its lifetime — the workspace session, the fragment store, and the two spec caches that hang off the same load. A second construction forks the reconcile state and the caches silently diverge: the fork answers from an empty cache while the original keeps ratcheting, so the cost the cache exists to remove comes back and nothing reports it.
- `mcp/env-through-seam` — Types in `SlideRule.Cli.Mcp.Infrastructure.*`, except types named `SystemEnvironment`, must not use `Environment.GetEnvironmentVariable()`, `Environment.GetEnvironmentVariables()`, `Environment.ExpandEnvironmentVariables()` or `Environment.SetEnvironmentVariable()`. A single IEnvironment seam keeps the MCP pipeline testable without mutating real process state: a test sets a variable on the fake, never on the process.
- `roslyn/no-msbuildlocator-query` — Types in `SlideRule.*` must not use `MSBuildLocator.QueryVisualStudioInstances()`. On .NET hosts QueryVisualStudioInstances returns no VS Setup instances, so code consulting it silently picks the wrong MSBuild; the sanctioned path is vswhere (VsWhereLocator). The quarantine's dragons warn this in prose — this rule is the teeth.
- `xunit/throws-setup-errors-only` — The Adapter layer must throw only `FileNotFoundException` or `InvalidOperationException`. The adapter runs inside consumers' test processes; its own failures must surface as the two documented setup errors, not as arbitrary exception noise beside the rule results.
- `analyzer/no-ambient-types` — The Core or Extraction layers must not reference `File`, `Directory`, `Environment`, `Console`, `Process`, `ProcessStartInfo` or `Random`. The analyzer package ships Core and Extraction in the directory the compiler loads the analyzer from, and the contract package ships a second Core copy beside its own analyzer, so both of these run inside csc: there is no console, the working directory belongs to whoever started the build, and one compiler server outlives many builds. RS1035 holds the analyzer projects to this list and cannot see the assemblies beside them. See <https://github.com/dotnet/roslyn/blob/3c9fedee40c44979ca893b6490ad5748bbb137b5/src/RoslynAnalyzers/Microsoft.CodeAnalysis.Analyzers/Core/AnalyzerBannedSymbols.txt>.
- `analyzer/no-ambient-members` — The Core or Extraction layers must not use `Path.GetTempPath()`, `Assembly.Load()`, `CultureInfo.CurrentCulture` or `CultureInfo.CurrentUICulture`. These four reach the same ambient world through types both layers otherwise use correctly — Path for path arithmetic, CultureInfo for the invariant culture, Assembly for reflection-only discovery — so the ban is member-level, where banning the types would red on code that is right.
- `exceptions/no-swallowed-broad-catches` — Types in the Core, Extraction, Analyzers, SpecAnalyzers, SpecCompletion, Workspace, Host, Adapter or Pack layers, except types named `ArchChecker`, `ArchRuleTests`, `BuildTierAnalyzer`, `CommandEntryPoint`, `IdleTimeoutWatchdog`, `ParentProcessWatcher`, `ServerShutdown`, `SpecLiteralAnalyzer` or `VsWhereLocator`, must not swallow `Exception`. A broad catch that holds the failure and continues holds the ones nobody thought about — a cancellation, an out-of-memory, the bug introduced two lines up — and hands the caller a wrong answer that reads like a right one. Two shapes are not that, and this rule passes both: a `when` filter is where a handler writes down what it is actually for, so everything else keeps travelling (`catch (Exception ex) when (ex is IOException or UnauthorizedAccessException)`); and a clause that ends in a `throw` — cleanup-and-rethrow, or translate-and-throw — suppresses nothing at all. The sanctioned handlers are exempt by type name rather than by site, the same granularity a baseline would give, stated in the spec instead of recorded in a file. See <https://learn.microsoft.com/dotnet/standard/design-guidelines/using-standard-exception-types>.
- `exceptions/no-bare-bcl-throws` — The Core, Extraction, Analyzers, SpecAnalyzers, SpecCompletion, Workspace, Host, Adapter or Pack layers must not throw `Exception`, `SystemException` or `ApplicationException`. A bare BCL exception type says only that something went wrong. A caller cannot filter on it, so throwing one forces every handler above into the swallowed broad catch `exceptions/no-swallowed-broad-catches` exists to prevent, and leaves a message string as the only thing left to match on. Nothing here throws one today; this rule is what stops the first one arriving unnoticed. See <https://learn.microsoft.com/dotnet/standard/design-guidelines/using-standard-exception-types>.
- `state/no-static-mutable` — Static fields of authored types in the Core, Extraction, Analyzers, SpecAnalyzers, SpecCompletion, Workspace, Host, Adapter or Pack layers that are not one of the sanctioned mutable statics (the Interlocked locations, the lock-guarded one-shot state, and the clock seam) must be readonly. A writable static is process-wide state in a library a long-lived MCP server calls concurrently and every spec project links: whoever wrote to it last decides what the next caller reads, and nothing in the type system says so. A const counts as readonly here — it is readonly's superset — so the law asks for the weakest thing that closes the hole.
- `naming/async-suffix` — Methods of authored types in the Core, Extraction, Analyzers, SpecAnalyzers, SpecCompletion, Workspace, Host, Adapter or Pack layers returning `Task`, `Task<TResult>`, `ValueTask` or `ValueTask<TResult>` whose name is not Rule_Holds or Workspace_LoadedCompletely (consumer-facing test display names) or WhenAllCallsComplete (a Task.WhenAll-style combinator) must be named `*Async`. House convention held repo-wide: an agent grepping *Async sees every await point; the three named exceptions are deliberate, not drift. See <https://learn.microsoft.com/dotnet/standard/asynchronous-programming-patterns/task-based-asynchronous-pattern-tap>.
- `naming/interfaces` — Interfaces in `SlideRule.*` must be named `I*`. Nearly every seam here is an interface — ISolutionSource, IEnvironment, IArchitectureSpec — and the `I` prefix is what lets a reader or an agent tell the port from its implementation at a glance, and what makes `I*` a reliable grep for the seams. A convention that holds for most types tells you nothing; this one is total. See <https://learn.microsoft.com/dotnet/standard/design-guidelines/names-of-classes-structs-and-interfaces>.

### Quarantined scopes
- `roslyn/msbuild-bootstrap` — Types in the Workspace layer in `SlideRule.Roslyn.MsBuild.*`, except types named `MsBuildBootstrap`, must be referenced only by types in the Workspace layer in `SlideRule.Roslyn.MsBuild.*` or types named `MsBuildBootstrap`. Fragile host bootstrap; contain it behind MsBuildBootstrap. Sanctioned surface: types named `MsBuildBootstrap`.
